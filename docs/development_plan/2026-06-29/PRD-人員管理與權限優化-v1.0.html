一、背景與目標

1.1 背景

MPS 採用 React 18 + TypeScript + Vite 前端、Supabase 後端，員工主數據來自 Bubble.io HR（Staff）。人員與權限相關資料分散在三張關聯表中：

  • staff_directory — Bubble 同步的 HR 快取（全量員工）
  • user_info — 分類（classification）與身份標籤（role_tag）
  • system_users — 登入白名單（Google OAuth 可登入者）

認證流程為 Google OAuth + 電郵白名單查詢；權限控制目前僅在「系統設定」模塊做前端角色門禁（canAccessSettings），docs/04-Role-Permission-RLS.md 中定義的完整 RBAC 矩陣與 RLS 政策尚未在資料庫層實施。人員相關三表 RLS 目前均為關閉狀態。

1.2 產品目標

編號目標說明
G1三表資料一致角色、狀態、電郵變更時，三表透過統一服務同步，消除「用戶管理改角色但登入仍用舊角色」等問題
G2單一開通路徑管理員只需一個入口完成「授予系統存取 + 分配角色 + 設定 Google 電郵」
G3登入安全補強登入時校驗 is_active、記錄真實登入日誌、移除不必要的 hardcoded bypass（或限於 dev 環境）
G4個人設定真實化個人資料、登入紀錄接入 Supabase，移除 mock 數據
G5權限體系對齊前端角色枚舉、Sidebar 過濾、角色權限頁與 04-Role-Permission-RLS.md 對齊；為 RLS 二期預留 accessible_companies 等欄位
G6代碼可維護拆分 SettingsModule.tsx（目前 >1600 行），消除重複邏輯

1.3 成功指標

  • 管理員在「用戶管理」修改角色後，該用戶下次登入/刷新即反映新角色（三表一致）
  • 停用帳號（is_active = false）無法完成登入授權
  • 登入紀錄頁展示來自 login_logs 表的真實數據
  • 非管理層用戶無法存取系統設定子頁（除個人設定）

四、現有業務流程（As-Is）

4.1 員工列表（StaffDirectory）

  1. 資料來源：優先從 staff_directory（Supabase）載入；若無則 fallback 至 Bubble API 即時查詢
  2. 管理員可從 Bubble 觸發 Edge Function sync-bubble-staff 全量/增量同步至 staff_directory
  3. 管理員可為每位員工設定 classification（system_user / other_staff / disabled）及 role_tag
  4. 點擊「儲存」→ 僅 upsert / delete user_info，不寫入 system_users
  5. office / department 變更會即時寫入 staff_directory + user_info

4.2 用戶管理（UserManagement）

  1. 讀取 system_users 全表展示白名單使用者
  2. 「從員工列表加入」→ insert system_users + upsert user_info（classification=system_user）
  3. 編輯使用者 → update system_users；僅在 google_email 變更時同步 user_info，role 變更不 sync
  4. 停用 / 啟用 → 僅 update system_users.is_active，不同步 user_info.system_status
  5. 移除 → delete system_users 記錄，不清理 user_info

4.3 登入認證（AuthContext）

Google OAuth 成功 → findSystemUserByEmail(email) ① 查 system_users（google_email / email，ilike） ② 查 user_info（google_email / email） → 若有 staff_id，再查 system_users.bubble_staff_id → 若仍無，bootstrap 合成 SystemUserProfile（id 非 UUID） → 若找到 sysUser： setSystemUser 查 user_info by staff_id → 用 role_tag/classification **覆蓋** systemUser.role 更新 last_login_at / auth_user_id logLoginEvent → login_logs → isAuthorized = systemUser 存在 AND (is_active === true OR is_active === null) → 系統設定門禁：canAccessSettings(systemUser.role)

4.4 個人設定（ProfileSection）

  1. 從 systemUser + staff_directory 動態載入姓名、部門、職位、電話
  2. 儲存電話 → 寫入 system_users.phone + staff_directory.work_phone
  3. 角色顯示為唯讀（來自 AuthContext enriched role）
  4. 角色分配（roleAssignments）仍為硬編碼 mock，使用 mockData 中的 companies/brands

4.5 角色權限（RolesSection）

靜態卡片列表，展示 7 個規範角色的模塊說明，不可編輯、未接入權限引擎，與 04 文檔矩陣不完全一致（缺少 super_admin 等擴展角色）。

六、目標業務流程與優化方案概要

6.1 設計原則

  • Single Source of Truth：以 bubble_staff_id 為關聯鍵；角色以 system_users.role 為權威來源，user_info 為冗餘快照（由同步服務維護）
  • Write Once, Sync Everywhere：所有寫操作經 personnelSyncService 統一處理三表
  • Fail Closed：登入時 is_active 必須明確為 true；查無白名單或已停用均拒絕
  • Backend Last Defense：前端門禁 + RLS 雙層（本期先做人員表 RLS）

6.2 目標架構

圖 6-1 目標三表同步架構（To-Be）

┌─────────────────────────┐ │ personnelSyncService │ │ (src/lib/personnel/) │ └───────────┬─────────────┘ │ ┌──────────────────────┼──────────────────────┐ ▼ ▼ ▼ staff_directory user_info system_users (HR 快取，Bubble 同步) (分類+標籤快照) (白名單+角色權威) 統一入口： • UserManagement — 主操作面（加入/編輯/停用/移除） • StaffDirectory — 批量分類（呼叫 syncService.grant/revoke） • ProfileSection — 僅寫個人欄位（phone 等） AuthContext： • 白名單查詢 system_users（is_active=true） • role 直接取自 system_users.role（不再被 stale user_info 覆蓋） • user_info 僅用於 classification 展示 / 員工列表

6.3 統一開通流程（To-Be）

  1. 管理員在用戶管理（或員工列表「設為系統使用者」）選擇員工
  2. 填寫：Google 電郵、角色、部門（可選）
  3. personnelSyncService.grantAccess() 原子操作：
    • upsert system_users（is_active=true, role, google_email…）
    • upsert user_info（classification=system_user, system_status=active, role_tag=role…）
    • 可選：更新 staff_directory.department / office
  4. 員工使用 Google 電郵 OAuth 登入 → 白名單命中 → 授權成功

6.4 停用 / 移除流程（To-Be）

操作system_usersuser_infostaff_directory
停用is_active=falsesystem_status=inactive, classification=disabled不變
重新啟用is_active=truesystem_status=active, classification=system_user不變
移除存取DELETEDELETE 或 classification=other_staff不變

八、非功能需求

8.1 安全

  • 生產環境禁止 anon 對 personnel 表的 unrestricted GRANT；改為 authenticated + RLS
  • system_users / user_info SELECT：authenticated 用戶可讀自己的記錄；management+ 可讀全部
  • system_users / user_info INSERT/UPDATE/DELETE：僅 management+ （或 service_role / Edge Function）
  • staff_directory：authenticated 可读；寫入僅 sync Edge Function（service_role）及 management+
  • Service Role Key 不得暴露於前端
  • 移除或限制 devBypassLogin 在 production build

8.2 RLS 政策（人員表 — 本期）

注意：現狀 migration 明確 DISABLE RLS 是為解決 OAuth 登入時 anon 查白名單問題。本期應改為：登入白名單查詢走 SECURITY DEFINER 函數（如 verify_system_user_by_email(email)），而非開放整表。
表政策概要
system_usersSELECT：self（by auth_user_id or email match）+ management；WRITE：management+
user_infoSELECT：self（by staff_id match）+ management；WRITE：management+
staff_directorySELECT：authenticated；WRITE：service_role + management
login_logsSELECT：management+；INSERT：authenticated（self）+ service

8.3 性能

  • findSystemUserByEmail 使用 SECURITY DEFINER 單查詢替代多次 ilike 並行（減少 cold start 延遲）
  • staff_directory 列表：Supabase 快取優先，Bubble 僅作同步源
  • login_logs 列表：索引 created_at DESC（已有）

8.4 可靠性

  • grantAccess / updateUser 失敗時事務回滾或補償日誌
  • 同步操作返回明確錯誤供 toast 展示

8.5 可維護性

  • ROLE_OPTIONS 單一定義於 src/lib/roles.ts
  • SettingsModule 拆分为独立组件（对齐 Settings.md 组件结构）
  • 补充 system_users / login_logs 至 supabase gen types
