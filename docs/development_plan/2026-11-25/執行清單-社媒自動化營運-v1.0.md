## 使用說明

1. 任務按依賴排序，**不要跳號執行**；標記 `⛔` 的任務擋住後續所有工作。
2. 每項完成後把 `☐` 改成 `☑`，並在「備註」欄寫下實際耗時或偏離原因。
3. 每個里程碑結束跑一次 **Gate**（見各段末尾），Gate 不過不進下一階段。
4. 所有路徑以 `D:\Project\MPS\` 為根，表格內省略前綴。
5. 檔案命名沿用 repo 慣例：migration `YYYYMMDDHHMMSS_描述.sql`、Edge Function 一個資料夾一支 `index.ts`。
6. **每次 `db push` 前後都要跑「SQL 安全審查」與「推送後回歸煙霧測試」**（見文件末段）。這兩項不是建議，是 Gate 的一部分。

### 禁止語句（PR 內出現即退回）

| 語句 | 原因 |
|---|---|
| `drop table` / `drop column` | 刪既有資料結構 |
| `alter column ... type` | 可能截斷或轉換失敗 |
| `truncate` / `delete from`（無主鍵條件） | 清空資料 |
| `drop policy` / `alter policy` | 改既有權限門禁 |
| `cron.unschedule` | 動到既有排程 |
| `update public.<既有表>` 無 `where` | 全表覆寫 |

## 回滾與安全網

回滾分四級，由輕到重。**永遠先做 L1，確認不夠再往下。**

| 級別 | 何時用 | 做法 | 影響 |
|---|---|---|---|
| L1 隱藏入口 | 插件有 bug、不想讓同事看到 | 移除 `AppContext` 的 `social-automation` 子項並重新部署前端 | 資料與函式全保留，零資料損失 |
| L2 停止生成 | 生成失控、成本超支、品質不對 | `update public.content_settings set daily_article_limit = 0, digest_enabled = false where id = 'default';` | 只影響插件；已排程 slot 轉 `held` |
| L3 停用排程 | cron 反覆失敗或造成負擔 | `select cron.unschedule('content-worker-tick');` 等四支逐一執行 | 只停插件排程；既有 job 不動 |
| L4 移除結構 | 確認整個放棄 | 見下方 | **會刪掉插件產生的全部資料** |

### L4 完整移除（最後手段）

**先備份，再明確逐張列出表名。禁止使用 `drop table content_*` 通配**——它會連 `content_publish_logs`（設計上 append-only 的回執）與 `content_assets` 一起清掉，而你可能只想移除其中一部分。

```sql
-- 0) 不可跳過：先備份結構與資料
--    npx supabase db dump --linked --schema public -f backups\before-rollback.sql
--    並把 content-assets bucket 內檔案另行下載

-- 1) 先移除排程，避免刪表過程中 worker 持續報錯
select cron.unschedule('content-worker-tick');
select cron.unschedule('content-planner-daily');
select cron.unschedule('content-digest-tick');
select cron.unschedule('content-health-daily');

-- 2) 依 FK 依賴反向刪除（子表先，父表後）
drop table if exists public.content_article_revisions;
drop table if exists public.content_publish_logs;
drop table if exists public.content_slots;
drop table if exists public.content_articles;
drop table if exists public.content_llm_usage;
drop table if exists public.content_jobs;
drop table if exists public.content_email_digests;
drop table if exists public.content_settings;
drop table if exists public.content_site_checks;
drop table if exists public.content_site_credentials;
drop table if exists public.content_site_pages;
drop table if exists public.content_site_sections;
drop table if exists public.content_sites;
drop table if exists public.content_assets;

-- 3) 可選：只移除新欄，不碰任何既有欄位
alter table public.seo_keywords
  drop column if exists last_used_at,
  drop column if exists pipeline_status,
  drop column if exists cluster,
  drop column if exists priority,
  drop column if exists intent;

-- 4) 只移除插件的儲存桶（確認檔案已備份）
delete from storage.objects where bucket_id = 'content-assets';
delete from storage.buckets where id = 'content-assets';
```

> 第 3、4 步是本清單中**唯一會刪既有資料**的動作（`seo_keywords` 新欄的值、bucket 內的內容包）。若只是想停用而非清除，做到第 1 步就夠。

| 其他情境 | 做法 |
|---|---|
| 日報誤寄 | 關閉 `content_settings.digest_enabled`；已寄內容可從 `content_email_digests` 追溯 |
| 憑證洩漏疑慮 | 輪換 `CONTENT_VAULT_KEY` 並重存憑證（**舊密文永久失效，不可逆**） |
| 用戶端版本落後（快取舊 JS） | 只隱藏入口（L1）即可，不要為此改資料庫 |
